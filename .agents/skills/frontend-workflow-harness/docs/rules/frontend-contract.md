# 프론트엔드 구현 계약

기획서가 화면 이름과 기술 스택만 나열하면 구현 범위가 정해지지 않는다. 사용자의 행동과 화면·서버 결과를 검증 가능한 인수 조건으로 쓴다.

## 사용자 여정과 화면 상태

기능 하나는 URL 개수가 아니라 사용자가 끝낼 일 하나를 기준으로 묶는다. '주문 목록 검색'은 검색·결과·빈 결과·오류 복구까지 같은 기능이다. 결제나 관리 기능을 끼워 넣지 않는다.

최초 로딩, 정상, 데이터 없음, 검색 결과 없음, 입력 오류, 서버·네트워크 오류, 비로그인·만료, 권한 없음, 처리 중·중복 제출, 성공·재방문을 확인한다. 기능에 없는 상태는 이유와 함께 해당 없음으로 남긴다. 모든 상태에 버튼을 억지로 만들지 않는다. 복구할 수 있는 상태에는 다음 행동을 알려준다.

## 상태와 API 경계

- 서버 데이터는 기존 캐시 계층, 공유할 검색·페이지 상태는 URL, 임시 입력과 열림 상태는 로컬 등 책임을 정한다. 같은 데이터를 여러 store에 복제하지 않는다.
- 요청·응답·오류·nullable·인증·페이지네이션을 실제 API 계약과 연결한다. 백엔드 필드와 상태 코드를 추측하지 않는다. 응답 필드 추가도 strict parser나 exhaustive 분기에 영향을 줄 수 있어 항상 안전하다고 가정하지 않는다.
- 검색어가 A→B로 바뀔 때 A의 늦은 응답이 B를 덮지 않게 한다. 취소 또는 최신 요청 확인을 검증한다. effect cleanup, 구독 해제, 타이머와 listener 정리를 확인한다.
- 쓰기 요청 중복 제출, 연타, 재시도, 타임아웃, 서버 중복 방지 계약을 확인한다. 낙관적 갱신에는 실패 롤백과 재조회 기준이 필요하다.
- cache key에 사용자·필터·페이지를 반영하고 mutation 후 무효화 범위를 정한다. 로그아웃 뒤 다른 계정의 데이터가 남지 않는지 확인한다.
- 직접 진입·새로고침·뒤로 가기·존재하지 않는 ID, 날짜·시간대·숫자 형식·IME 조합을 처리한다.

## UI·디자인

접근 가능한 디자인 원본과 확인한 node/version을 기록한다. 접근하지 못한 Figma 화면을 봤다고 하지 않는다. 주어진 화면이 없으면 기존 앱의 토큰·공통 컴포넌트·실제 콘텐츠를 기준으로 초안을 만들고 가정을 표시한다.

기존 정보 구조와 타이포그래피를 먼저 맞춘다. 긴 한국어·주소·오류 메시지, 좁은 화면에서의 순서·줄바꿈·overflow를 확인한다. 텍스트로 의미가 드러나는 조작을 우선하고, 아이콘은 프로젝트 규칙과 접근성 이름을 따른다. 다른 프로젝트의 취향을 새 앱에 강제로 적용하지 않는다.

## 접근성

native button/link/input과 연결된 label을 우선한다. 키보드 동선, 보이는 focus, dialog 진입·탈출·복귀, 오류 연결과 필요한 상태 알림을 확인한다. 색만으로 결과를 구분하지 않는다. 대비·목표 크기·reflow 기준은 프로젝트 접근성 목표와 아래 원문으로 확인한다. 자동 검사 통과를 전체 접근성 준수로 표현하지 않는다.

## 보안·렌더링·운영

- UI의 버튼 숨김은 서버 인가를 대체하지 않는다. 공개 bundle에 비밀키를 넣지 않는다. 토큰 저장·갱신은 기존 인증 계약을 따른다.
- HTML 삽입, 사용자 URL·redirect, 파일 업로드, 로그와 분석 이벤트의 개인정보를 검토한다. 테스트 픽스처에 실제 사용자 데이터를 넣지 않는다.
- SSR 앱은 browser API 접근, server/client 경계, hydration, 서버 캐시의 사용자 격리와 오류 경계를 확인한다. 해당 프레임워크가 없으면 억지로 도입하지 않는다.
- 새 dependency는 기존 수단으로 해결하기 어려운 이유, bundle·유지보수 비용을 검토한다. 성능은 같은 환경의 변경 전후 수치로 판단한다. 측정 없이 '최적화'라고 보고하지 않는다.
- 위험한 변경은 플래그·롤백과 API 호환 기간을 정한다. 삭제·결제 등의 실제 작업은 테스트 계정과 환경을 확인한다.
