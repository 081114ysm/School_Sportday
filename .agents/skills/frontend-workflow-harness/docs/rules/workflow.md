# 기능 하나의 전체 흐름

이 하네스는 사용자 여정 하나를 구현하고 검증해 PR로 전달하는 절차다. 원본의 기능 단위·승인·범위 통제를 유지하고, 프론트엔드의 화면 상태와 브라우저 검증을 완료 조건에 포함한다.

## 상태와 결과물

| 단계 | 수행할 일 | 다음 단계로 가는 근거 |
|---|---|---|
| plan | 기존 구현·원본 확인, 인수 조건·상태·API·검증 계획 작성 | 현재 기획서와 설정에 적용되는 사용자 승인 |
| implement | 승인 범위 구현, 필요한 회귀 테스트, 명령 검사 | 리뷰 가능한 diff |
| review | 실제 diff와 인접 호출부 검토, 결함 수정 | 현재 코드의 리뷰 보고서 |
| qa | 사용자 여정·상태·브라우저 검증 | 자동 검사와 브라우저 증거 |
| ready | 변경·검증·미검증·롤백 정리 | 현재 코드에 대한 PR 생성 권한 |
| pr | PR 생성, 현재 PR head의 CI·리뷰 피드백 반영 | 성공한 CI와 실제 머지 증거 |
| done | 통합 브랜치 머지 확인, 이슈 정리 | 다음 기능 착수 가능 |

사용자는 기능을 설명하고, 에이전트가 [자동 사이클](agent-cycle.md)을 수행한다. `harness.mjs`는 로컬 상태·검증을, `github.mjs`는 실제 이슈·PR 작업을 담당한다. Git 브랜치·push·머지·배포는 사용자 지시 범위를 확인한 에이전트가 수행한다.

## 착수

1. 대상 프로젝트의 지시, README, 패키지·lockfile, route·컴포넌트·API 계층과 기존 테스트를 읽는다. `doctor` 결과와 실제 문서를 대조한다.
2. 활성 state와 실제 브랜치를 읽는다. 다른 기능이 진행 중이면 재개하거나 사용자 지시에 따라 정리한다. 아이디어 언급만으로 원격 이슈를 만들지 않는다.
3. 확인된 통합 브랜치에서 기능 브랜치를 먼저 만든다. 기획서도 이 브랜치에서 관리한다. 원본의 '기획서 먼저, 브랜치 나중' 모순을 피한다. 미커밋 사용자 변경은 보존하고 다른 기능과 섞지 않는다.
4. `start`로 상태와 기획서 틀을 만든다. GitHub를 쓰면 승인된 범위 내에서 이슈를 만들고 URL을 연결한다. 리모트가 없으면 로컬 ID로 진행할 수 있다.

## 승인

`approval.plan`과 `approval.pr`의 기본값은 true다. 사용자가 이미 구체적인 범위와 실행 권한을 부여했다면 해당 지시를 기록하고 계속한다. 과거의 포괄적인 말로 새 정책까지 승인됐다고 해석하지 않는다. 별도의 승인 질문이 필요하면 검토할 기획서 또는 결과를 먼저 완성한다.

- plan 승인: 포함·제외 범위, 인수 조건, 실제 기획서 버전, API·UX 계약.
- pr 승인: 실제 diff, 검사·브라우저 결과, 남은 위험을 기준으로 하는 생성 권한.
- 각 지시 원문과 출처·시각을 기능의 `evidence/` 안에 기록하고 `approve`로 연결한다. 에이전트가 사용자 승인 문장을 만들어서는 안 된다.
- 설정에서 승인 게이트를 끄는 선택은 프로젝트 소유자가 한다. 외부 동작 권한까지 생기지는 않는다.

## 구현 중 변경

| 계속할 수 있는 구현 세부사항 | 계약 변경으로 재검토할 항목 |
|---|---|
| 내부 함수 분리, 변수명, 동작이 같은 컴포넌트 분리, 요청 취소 구현 | 사용자 여정, 필수 입력, URL·쿼리 의미, API schema, 인증·권한, 오류·재시도 정책, 디자인 주요 배치 |

내부 변경도 관련 문서를 실제 구현과 맞춘다. 승인 기획서를 수정하면 해시가 바뀌므로 CLI 승인 기록은 다시 연결해야 한다. 계약이 바뀌면 `replan --reason ...`으로 승인과 검증 기록을 비우고 영향을 설명한다. 재승인 전까지 의존 구현을 멈춘다.

## 검증과 전달

구현 → 리뷰 → QA 순서로 진행한다. QA에서 발견한 같은 범위의 버그는 같은 브랜치에서 고친다. 수정 후 코드가 바뀌었으면 리뷰와 검사·브라우저 증거를 다시 남긴다. 검사만 초록색이라고 화면이 검증된 것은 아니다.

PR 생성 전 로컬 검사·리뷰·브라우저 증거를 갖춘다. PR에서만 실행되는 CI는 생성 전에는 pending으로 적는다. 생성 뒤 현재 head의 CI를 확인한다. PR 생성·머지·배포는 각각 다른 동작이며, PR 생성 권한으로 나머지를 추론하지 않는다.

CLI `done`은 통합 브랜치에 머지된 상태다. 사용자 요청이 구현 또는 PR 전달까지라면 그 범위에서 결과를 전달하고 state를 해당 단계에 남긴다. 사용자 응답이 없다고 승인이나 머지를 만들어내지 않는다.
