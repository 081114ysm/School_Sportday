# 진행 기록과 세션 복구

`.frontend-workflow/state.json`이 현재 단계의 단일 기준이다. 기능별 archive는 `.frontend-workflow/features/{id}/state.json`이다. GitHub 이슈는 이 상태의 공유용 요약이며 별도의 수작업 단계 상태를 동시에 운영하지 않는다.

GitHub 모드에서는 에이전트가 단계가 바뀔 때 `github.mjs issue-sync`로 이슈 체크리스트와 결과 경로를 갱신한다. 재개 시에는 `github.mjs resume`으로 이슈부터 읽고 실제 로컬·버전 관리 증거와 대조한다. 원격 블록이 다른 곳에서 바뀌었다면 자동 덮어쓰기를 멈춘다. 원격 편집은 API 차원의 원자적 compare-and-swap이 아니므로 여러 에이전트가 같은 이슈를 동시에 갱신하지 않는다.

## 기록할 것

- 기능 ID, 이슈 URL(선택), 작업 브랜치, 최초 base SHA, 기획서 경로.
- plan/pr 승인 근거 파일과 해시, 현재 기획서·설정 해시.
- 자동 검사 결과, 리뷰·브라우저·CI·머지 보고서와 파일 해시.
- 기록에서 자동 생성한 기능별 `QA.md`. 이슈 진행 블록에도 해당 경로를 표시한다.
- 단계 변경·재기획·검사·승인 이력과 시각.

상태와 기획서·정제한 증거는 Git으로 관리한다. 로그·쿠키·토큰·민감한 실제 사용자 화면을 커밋하지 않는다. 모든 기능 증거는 해당 기능의 `evidence/` 안에 둔다. 이 폴더는 코드 지문에서 제외하며, 증거별 파일 해시로 별도 확인한다.

`QA.md`는 기능 디렉터리에 함께 커밋할 읽기용 요약이다. 원본 사실은 state와 evidence이며 수동으로 쓴 Markdown을 게이트 통과 근거로 읽지 않는다. 자동 영역 밖의 메모는 보존한다. 코드·기획·설정·증거를 직접 수정했다면 `qa-report`로 새 문서를 만들고 재검증이 필요한 항목을 확인한다.

## 재개

```sh
node scripts/harness.mjs status
git status --short
```

대상 경로·브랜치·이슈·인수 조건·현재 diff와 증거의 유효성을 대조한다. stage가 ready여도 `validChecks`나 `validEvidence`가 false이면 다시 검증한다. 코드가 바뀌면 기존 지문과 일치하지 않는다. 기획서·설정 변경도 승인을 무효로 한다.

Git 브랜치를 바꾸거나 reset·rebase한 사실을 상태만으로 숨기지 않는다. PR 단계에서 새 head가 생기면 CI도 다시 실행한다. 예전 커밋의 성공을 새 커밋에 가져오지 않는다.

## 동시 실행과 복구

변경 명령은 `.frontend-workflow/.lock/owner.json`에 PID와 시작 시각을 기록한다. 다른 실행은 거부한다. 비정상 종료 뒤 lock이 남으면 해당 PID가 실제로 종료됐는지 먼저 확인하고 lock만 제거한다. 실행 중인 검사를 무시하고 삭제하지 않는다.

상태는 임시 파일을 rename해 저장한다. feature archive를 먼저, active pointer를 나중에 저장한다. 둘 사이의 비정상 종료로 다르면 시간·history와 실제 파일을 대조해 archive의 최신 검증 가능한 상태를 복구한다. state를 수동 편집해 게이트를 통과한 것으로 만들지 않는다.

진행 중 다른 독립 기능이 들어오면 현재 범위를 사용자와 확인한다. 명시적인 전환 지시를 무시하며 '한 번에 하나'를 강제하지 않는다. 현재 기능의 상태·변경을 보존하고, 별도 worktree/저장소로 분리할지 결정한다. CLI는 같은 작업 폴더의 두 번째 활성 기능을 거부한다.
